## Do now

### 1. Update Next.js in cdl-pipeline (critical)

Next.js 16.3.1 has two holes an attacker can reach over the network with no login:

- **Unauthenticated RCE through the image optimization API** (GHSA-2464-fhr4-w9xw). Someone uploads a crafted SVG; your server runs their code.
- **Unauthenticated RCE through `next/og` image generation** (GHSA-vcvr-r3jv-pc5j).
- Plus a cache-poisoning bug that can swap content between users, and about ten smaller advisories in the same version.

The dashboard's Basic auth does not cover these paths — they're part of the app itself, and the Fly app is public.

**Fix:**
```bash
cd cdl-pipeline
bun update next
git add bun.lock package.json
git commit -m "security: update next to 16.4.x"
git push   # deploys as usual
```

Your website repo already runs 16.4.3, so that's a known-good target. This same update also clears most of the other vulnerable packages found in the lockfile (14 of 17 flagged, including everything below).

### 2. The same update clears these (they ride along)

- **@modelcontextprotocol/sdk 1.30 → 1.32.2** — six advisories. The two that matter since `/api/mcp` is public: bearer auth accepted tokens issued for a different tenant, and the OAuth client could leak credentials to a malicious auth server.
- **undici** — TLS certificate validation bypass and cross-user cache disclosure.
- **hono + @hono/node-server** — XSS and a path-traversal class bypass in static file handling.
- **body-parser, systeminformation** — lower stakes; systeminformation's command injection is Windows-only and you deploy on Linux.

**Fix:** covered by `bun update` from step 1. Commit and redeploy once.

### 3. Compare tokens with timingSafeEqual (small, two lines)

`src/api/auth.ts` line 13 checks the bearer token with `token !== expected`. That's fine functionally, but a `!==` string compare leaks timing information in theory. You already do this the right way in `src/lib/mcpAuth.ts` (line 40) — copying that pattern keeps it consistent:

```ts
import { timingSafeEqual } from "node:crypto";

const expected = Buffer.from(API_TOKEN);
const got = Buffer.from(token);
if (expected.length !== got.length || !timingSafeEqual(expected, got)) {
  return Response.json({ error: "unauthorized" }, { status: 401 });
}
```

## Worth scheduling (not urgent)

### 4. The pipeline Dockerfile runs as root

`cdl-pipeline/Dockerfile` (around line 42, before the `CMD`) never switches to a non-root user. If the app is ever compromised, the attacker lands as root in the container.

**Fix:** add before the `CMD` line:
```dockerfile
USER bun
```
(Bun's official image ships a `bun` user. If you use a plain node image, use `USER node`.)

### 5. Pin GitHub Actions to commit SHAs

Five `uses:` lines across your workflows (cdl-pipeline `ci.yml` lines 31, 32, 69, 70; website `lighthouse.yml` lines 17, 18, 37) point at action tags like `@v4`. Tags are mutable — if the action's repo is ever compromised, your CI runs attacker code with your secrets.

**Fix:** pin each `uses:` to the commit SHA of the version you're on (GitHub shows it on the action's releases page), with the version as a comment:
```yaml
uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
```

### 6. Row-level security is missing on 21 pipeline tables (defense in depth)

21 tables in cdl-pipeline's Supabase migrations (`contacts`, `campaign_emails`, `entities`, `entity_addresses`, and others) have no `ENABLE ROW LEVEL SECURITY`. Today this is **not directly exploitable**: the pipeline talks to Postgres over a direct `DATABASE_URL` connection from the server, and the API is token-gated — there's no anon key reaching browsers. But RLS is your safety net for the day any of that changes.

**Fix (can be one migration):**
```sql
ALTER TABLE contacts ENABLE ROW LEVEL SECURITY;
-- repeat per table, then add policies that match how each table is accessed,
-- or leave them deny-by-default since access flows through the API only
```
The website repo already does this properly — its pattern (a follow-up `_rls.sql` migration) is a good template.

### 7. Website header hygiene (medium effort, no rush)

The passive ZAP scan of customsdatalock.com and portal.customsdatalock.com found no high-risk issues — 18 low/medium notes, mostly:

- **CSP uses `unsafe-inline`** for scripts and styles (both sites). This is the Next.js default and needs nonce-based work to fix properly; worth doing eventually, not an emergency.
- **Missing cross-origin headers** on the portal: `Cross-Origin-Opener-Policy`, `Cross-Origin-Embedder-Policy`, `Cross-Origin-Resource-Policy`. One-line additions to the Fly/Next config.
- **`X-Powered-By` leaks the framework** on the portal: set `poweredByHeader: false` in next.config.
- One subresource loaded without an integrity attribute on the marketing site.

**Fix (portal, next.config.mjs):**
```js
poweredByHeader: false,
async headers() {
  return {
    source: "/(.*)",
    headers: [
      { key: "Cross-Origin-Opener-Policy", value: "same-origin" },
      { key: "Cross-Origin-Resource-Policy", value: "same-origin" },
    ],
  };
},
```
